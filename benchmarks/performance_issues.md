# Performance issues: `compile` and `helion` backends

**Method.** Shape `(16384, 16384)`, B200, peak 8 TB/s. Each gist is the Triton captured from the
frozen kernel as of this commit — `compile` via `TORCH_LOGS=output_code` on the
`torch.compile(flex_tile_map, INDUCTOR)` path that lowers the gold `pt_ref_fn` (`benchmark.py`
`_bench_one`), `helion` via `HELION_PRINT_OUTPUT_CODE=1`.

## backend = compile

| recipe | pct_bandwidth | gaps |
| --- | --- | --- |
| mxfp8_floor_dim_m | 17.5% | [generated triton](https://gist.github.com/vkuzo/fe1e0e695982ff83cee9343932e5bfe3) — The gold recipe is one logical pass: read each (32,1) column block once, abs-max down the 32 rows, quantize to fp8 with an e8m0 scale, store transposed. Inductor instead emits **two** Triton kernels (see gist): kernel 0 is the abs+amax reduction, kernel 1 **re-reads x**, does the e8m0 bit-math (rshift/bitwise_and/sub/clamp) and writes the transposed (`aten.t`+`clone`) fp8 output. So x is streamed twice and the dim-M store is a narrow, poorly-coalesced transposed write — the two costs the manual triton/cute kernels (best 63.6%) fuse into one pass over a register-resident tile. <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/149982) |
| mxfp8_floor_dim_m_swizzle | 18.4% | [generated triton](https://gist.github.com/vkuzo/ed8d8fe504716a6bbef051ad5a6b9ba8) — Same two-kernel reduce-then-re-read-and-quantize split as plain dim-M, with the swizzled scale layout adding permute/reshape work in the store. Because the quantize depends on the per-column amax it can't fuse with the reduction, so x is read twice and the transposed fp8 store stays 32-wide. The manual triton/cute swizzle kernels do it in a single pass and reach ~74% (best 73.9%). <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/149982)  |
| fp8_deepseek_1x128_dim_m | 40.8% | [generated triton](https://gist.github.com/vkuzo/b77c73f506130babdb8ac161938d1e96) — The least-bad compile dim-M case: 128-row groups mean fewer scales and a wider (128) transposed store than the mxfp8 dim-M kernels. But inductor still splits it into two kernels — amax reduction, then a second kernel that **re-reads x** and writes the transposed fp8 tile — so x is streamed twice and the store is a strided transpose, versus the single register-resident pass the triton kernel does (71.7%). <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/149982)  |
| mxfp8_floor_dim_km | 19.2% | [generated triton](https://gist.github.com/vkuzo/d5cf0ef71aa70c9dadcdacafd2caac50) — The gold recipe reads x once and reduces it both along K (1×32) and M (32×1) to emit two quantized outputs plus two scale sets in one pass. Inductor treats dim-K and dim-M as independent subgraphs and further splits dim-M's reduce-from-normalize, emitting **three** Triton kernels that each re-read x (**x streamed 3×**), with the transposed dim-M store as the binding cost. The 32-block granularity also means 4× as many e8m0 scales as the 128-block deepseek variant. Best manual (cute) 57.1%. <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/149982)  |
| mxfp8_floor_dim_km_swizzle | 19.9% | [generated triton](https://gist.github.com/vkuzo/a930fc5715a47296620b33934ad066dc) — Same three-kernel, x-streamed-3× structure as the plain dim-km kernel, with the swizzled scale layout on top (dim-K fused reduce+quantize, dim-M amax, dim-M quantize+transposed-store). The inability to share x's load across the K and M subgraphs is the core inefficiency the one-pass manual kernels avoid (best cute 62.3%). <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/149982)  |
| fp8_deepseek_1x128_dim_km | 35.8% | [generated triton](https://gist.github.com/vkuzo/191407ae5e73a2f87da6ca698c1f19e7) — 128-blocks write 4× fewer scale values than the mxfp8 32-block dim-km, so this is ~2× its bandwidth, but the same structural problem holds: inductor emits **three** Triton kernels that each read x (dim-K and dim-M are independent subgraphs, dim-M splits reduce-from-normalize). The ~35.8% is the cost of ~3 passes over x plus a transposed dim-M store, not the intended single pass (triton 57.9%). <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/149982) |
| mxfp8_32x32_floor | 26.6% | [generated triton](https://gist.github.com/vkuzo/9ff41c01ac855da12e26217a2d1759b5) — The (32,32) square-block quant is emitted as two kernels (block amax reduction, then a **re-read-x** quantize) rather than one register-resident pass. The strided 32×32 block access can't be both vectorized and warp-coalesced; the hand triton kernel (78.3%) loads the whole block directly into registers and reduces/quantizes in place — a register/tile pattern inductor doesn't reproduce here. <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/191338) |
| fp8_deepseek_128x128 | 44.4% | [generated triton](https://gist.github.com/vkuzo/e7a7451f10fea49079fe747eac899437) — Emitted as two Triton kernels: a reduction with transpose+clone, then a quantize kernel that **re-reads x** plus the scale and writes a transposed fp8 tile. So x is streamed twice and the 128×128 store is transposed. The hand triton kernel keeps the whole 128×128 tile register-resident (direct gmem→register load, reduce, quantize, store) for a single-pass 77.1%; that register-resident direct-load model is a triton-only win inductor can't match here. <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/191338) |
| nvfp4 | 23.0% | [generated triton](https://gist.github.com/vkuzo/9aeb26fe77c6c57760f1b1d229f1d688) — The fp4 (1×16) cast is split into two kernels: a per-16-block amax reduction, and a quantize kernel that **re-reads x**, computes the e4m3 inner scale, and writes the fp4-packed data. So x is streamed twice, and the packed even/odd nibble write plus the extra scale read keep it well under the single-pass triton kernel (66.7%). The fp4 encode itself isn't the bottleneck (~60% in isolation). <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/167098) |
| nvfp4_swizzle | 22.3% | [generated triton](https://gist.github.com/vkuzo/930577de9b595df3803bdefceef93697) — The worst nvfp4 case: inductor emits **three** kernels — abs+amax reduction, a quantize kernel that re-reads x for the fp4-packed data, and a separate permute/transpose/clone kernel that scatters the swizzled inner scale (the gist shows the 5D permute chain). So x is streamed twice and the swizzle is a standalone scatter, versus the one fused pass the manual kernels use (best cute 64.1%). <br/><br/> [issue](https://github.com/pytorch/pytorch/issues/167098) |
| bf16_rht | 29.3% | [generated triton](https://gist.github.com/vkuzo/d4a16393694ececdb05e2c8dde1f07c3) — Not extra traffic — the whole ~1.07 GB (read x, write out) is useful. The 16×16 Hadamard `x.reshape(...,16) @ rht` is lowered to a single cuBLAS GEMM via `extern_kernels.mm`, shape (16777216, 16) @ (16, 16), i.e. K=N=16 (the gist has **no `@triton.jit` at all**, just the extern mm). That skinny GEMM tiles terribly (wasted N-tiling, no K-reuse) and runs on the compute path, so a memory-bound op (~4 flop/byte) fails to saturate DRAM — ~29% vs the manual kernels' ~68% (best cute 68.2%), which run it as a bandwidth-bound elementwise transform. |
| fp32_to_bf16_sr | 29.6% | [generated triton](https://gist.github.com/vkuzo/7b1d4635cb7d80cf67a0a25b6a51e2e9) — The stochastic-rounding uniform is drawn via `aten._philox_uniform`, which inductor treats as an opaque extern op rather than fusible in-kernel RNG. So it runs as two DRAM passes: the philox extern materializes a full-size fp32 random tensor, then one Triton kernel (the gist's single `@triton.jit`) reads it back alongside x to dither+truncate. That wasted RNG round-trip roughly doubles real traffic; the manual triton/cute kernels draw the uniform inside the kernel (no materialized random tensor) and hit 73–85% (best cute 84.8%). |

## backend = helion

Helion caveat: most of these pin a single `helion.Config` (a **correctness-first** debug loop)
rather than running a live autotune search — treat them as a functional baseline, not a fully-tuned
comparison. Two exceptions (`fp8_deepseek_1x128_dim_m`, `mxfp8_floor_dim_m`) use genuine tuned-shape
configs and land close to their triton counterparts.

| recipe | pct_bandwidth | gaps |
| --- | --- | --- |
| fp8_deepseek_1x128_dim_m | 66.8% | [generated triton](https://gist.github.com/vkuzo/1b61c2032107e73981b7e7a3d569f9cc) — Smallest gap in the table. Real pinned config (`block_sizes=[1,128]`, `reduction_loops=[None]` so the 128-row reduction is persistent and x is loaded once) with the dim-M transposed store done in-kernel via a register permute (like `tl.trans`). Within a few points of its bespoke triton counterpart (71.7%); the residual is the same occupancy-vs-coalescing bind the triton kernel faces, not a helion-specific loss. |
| mxfp8_floor_dim_m | 55.2% | [generated triton](https://gist.github.com/vkuzo/1760bf572346ba95c7646e25d083033d) — Also a genuine pinned config (`block_sizes=[4,32]` = a 128-row group, `reduction_loops=[None]`), reducing per 32-row sub-block to e8m0 scales and storing transposed in-kernel. It trails the triton/cute dim-M kernels (~60–64%, best cute 63.6%) for the same reason those trail SOL: the heavier mxfp8 math (4 scales/column, e8m0 bit-work, the fp32 working tile) drives register pressure that forces a narrower tile — a register/occupancy bind, not an emitter artifact. |
| mxfp8_floor_dim_m_swizzle | 36.7% | [generated triton](https://gist.github.com/vkuzo/1bf89071aeedcc807a41588365b4e6e6) — Correctness-first pin. To make the swizzled scale store a plain index it tiles over the block-count dims, forcing the within-block 32/128 axes into 5D register tiles; `autotune_effort="none"`'s default heuristic would blow the register tile past triton's 1,048,576-element per-tensor cap at this shape, so it's pinned to `block_sizes=[1,1]` (one 128×128 block/program). That un-tuned tile is why it trails the plain dim-M helion kernel and the manual swizzle kernels (best cute 73.9%); raising the block size is the perf follow-up. <br/><br/>[issue](https://github.com/pytorch/helion/issues/3176) |
| mxfp8_floor_dim_km | 24.9% | [generated triton](https://gist.github.com/vkuzo/a2886db8adae3d175c1c461820992bf7) — One read of x feeds both the dim-K and dim-M reductions off a single loaded 32×32 block-grid view, but it's pinned to `block_sizes=[1,1]`: `autotune_effort="none"` is unusable here (the default heuristic scales the register tile by block²·32·32 and overflows the per-tensor cap / doesn't compile). Low bandwidth is expected on this correctness-first tile — one x read but ~2× the output writes (four tensors, 4× more e8m0 scales than the 128-block variant). Best manual (cute) 57.1%. <br/><br/>[issue](https://github.com/pytorch/helion/issues/3176) |
| mxfp8_floor_dim_km_swizzle | 27.1% | [generated triton](https://gist.github.com/vkuzo/fbb47022b3bc4ccf151a44e60b5a2542) — Views x with both within-128 axes fully split so one loaded block feeds both reductions and both scale stores via pure permutes. Same `block_sizes=[1,1]` pin / autotune-none overflow as the other dim-km kernels; a hair faster than the plain dim-km (24.9%), consistent with the swizzled scale store beating the plain strided one. Un-tuned tile, not a framework wall (best cute 62.3%). <br/><br/>[issue](https://github.com/pytorch/helion/issues/3176) |
| fp8_deepseek_1x128_dim_km | 46.9% | [generated triton](https://gist.github.com/vkuzo/3902106acb5b0f396bc52442ac350b9f) — ~2× the bandwidth of the mxfp8 dim-km because 128-blocks write 4× fewer scale values (in larger contiguous chunks). Pinned `block_sizes=[1,1]` for the same register-tile-overflow reason as the others, so it's a correctness-first baseline that trails the one-pass triton kernel (57.9%). <br/><br/>[issue](https://github.com/pytorch/helion/issues/3176) |
| mxfp8_32x32_floor | 52.2% | [generated triton](https://gist.github.com/vkuzo/1e36be92956ec5cb9a31fbc6f6149ff6) — Deliberately pinned to a tiny `block_sizes=[1,1]` (one 32×32 block/program): the default heuristic's [16,16] materializes a ~1 MB fp32 register tile that takes ptxas ~18 s to compile cold, so [1,1] keeps it at ~4 KB for a fast debug loop. That fast-compile tile, not the emitter, is why it trails the register-resident triton kernel (78.3%). <br/><br/>[issue](https://github.com/pytorch/helion/issues/3176) |
| nvfp4 | 26.1% | [generated triton](https://gist.github.com/vkuzo/aa20244d52aae63d4e954461860885b0) — The fp4 encode+pack uses the hardware `cvt.rn.satfinite.e2m1x2.f32` PTX via `hl.inline_asm_elementwise`, and runs on `autotune_effort="none"` (default config) because `autotune_effort="full"` crashes on that inline-asm HOP. Bit-exact but un-tuned — the low bandwidth is the default config plus the extra even/odd split work, not the encode itself (triton 66.7%). <br/><br/>[issue](https://github.com/pytorch/helion/issues/3177) |
| nvfp4_swizzle | 37.4% | [generated triton](https://gist.github.com/vkuzo/a9585e57098116ebc2053c42068c135d) — ~1.4× the plain nvfp4, again because the swizzled scale store beats the plain strided one. Pinned `block_sizes=[1,1]`; `autotune_effort="none"` isn't usable here for two reasons at once — the inline-asm autotuner crash nvfp4 also hits, and the swizzle tile-shape overflow the other swizzle kernels hit. Un-tuned correctness baseline (best cute 64.1%). <br/><br/>[issue](https://github.com/pytorch/helion/issues/3176), [issue](https://github.com/pytorch/helion/issues/3177) |
